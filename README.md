# جی‌پی‌تی‌یار — پنل مدیریت و ربات بله

پنل فارسی، راست‌به‌چپ و واکنش‌گرا برای فروش و تمدید اشتراک ChatGPT Plus در بله، با قیمت پیش‌فرض روزانه **۳۵٬۰۰۰ تومان**.

## راه‌اندازی مدیر

لینک راه‌اندازی اختصاصی در گفتگو تحویل می‌شود؛ این لینک و کد آن در مخزن ذخیره نمی‌شوند. لینک تا ۷ روز معتبر است و پس از فعال‌سازی مدیر، دوباره قابل استفاده نیست.

۱. لینک را باز کنید و نام کاربری و رمز دلخواه با حداقل ۱۲ نویسه بسازید.
۲. در **Ente Auth** گزینه افزودن حساب را بزنید و QR نمایش‌داده‌شده را اسکن کنید. QR داخل مرورگر تولید می‌شود و به سرویس دیگری ارسال نمی‌شود.
۳. کد ۶ رقمی را وارد کنید و ۸ کد بازیابی یک‌بارمصرف را در محل امن نگه دارید.
۴. در «اتصال‌ها»، **توکن ربات بله**، **توکن پرداخت کیف‌پول بله** و **توکن مدیریتی اکستنشن** را ثبت کنید.
۵. پس از تأیید اتصال ربات و اکستنشن، فروش را فعال کنید. ذخیره توکن پرداخت به‌تنهایی اثبات صحت آن نیست؛ تأیید نهایی در تراکنش واقعی انجام می‌شود.

توکن پرداخت با توکن ربات تفاوت دارد و از BotFather بله برای **همین ربات** دریافت می‌شود. توکن آزمایشی کیف‌پول برای فروش واقعی پذیرفته نمی‌شود.

## تغییر توکن‌ها

در «اتصال‌ها»، توکن جدید را در کارت ربات بله، کیف پول یا اکستنشن وارد کنید و «بررسی و جایگزینی» را بزنید. وجود سفارش یا اشتراک قبلی مانع تغییر توکن یا انتخاب حساب جدید نیست. اعتبار ربات و دسترسی مدیریتی اکستنشن پیش از ذخیره بررسی می‌شود؛ توکن‌ها رمزگذاری می‌شوند و مقدار ذخیره‌شده در پنل نمایش داده نمی‌شود.

تعویض توکن همان ربات، کیف پول و وب‌هوک آن را حفظ می‌کند. اگر **ربات دیگری** انتخاب شود، وب‌هوک جدید تنظیم، وب‌هوک ربات قبلی قطع، اتصال کیف پول قبلی پاک و فروش غیرفعال می‌شود؛ توکن کیف پول مخصوص ربات جدید را ثبت و فروش را دوباره فعال کنید. شناسه آپدیت و کلید ایجاد سفارش به شناسه ربات وابسته است تا ربات جدید با سوابق ربات قبلی تداخل نکند.

با انتخاب **حساب اکستنشن دیگری**، فروش تا فعال‌سازی دوباره متوقف می‌شود. سفارش‌ها و اشتراک‌های قبلی همراه شناسه حساب اولیه نگه داشته می‌شوند؛ انتقال خودکار بین حساب‌ها انجام نمی‌شود. برای ادامه عملیات روی سوابق آن حساب، توکن مدیریتی همان حساب را ثبت کنید. شناسه اشتراک یکسان در دو حساب، دو رکورد جدا دارد. صورتحساب‌های حساب یا ربات قبلی از اتصال جدید قابل پرداخت نیستند.

پنل و API فقط سه اتصال بالا را پشتیبانی می‌کنند. کد، فرم، بررسی اتصال، وب‌هوک و مسیر پرداخت پیام‌رسان حذف‌شده در نسخه فعلی وجود ندارد؛ ارتقای دیتابیس نیز توکن‌ها و RPCهای قدیمی آن را حذف می‌کند و سوابق تجاری را نگه می‌دارد.

برای فعال‌شدن این تغییر در نصب موجود، ابتدا `supabase/migrations/20261026200939_gpyb_replace_integration_tokens_remove_legacy_messaging.sql` را پس از ارتقاهای قبلی در همان پروژه اجرا کنید، سپس Edge Function به نام `gptyar-bale` را از کد جدید منتشر کنید. خروجی جدید `index.html` و `assets/` نیز باید در GitHub Pages منتشر شود. اجرای دوباره `schema.sql` روی دیتابیس موجود لازم نیست؛ این فایل مخصوص نصب تازه است. توکن‌های واقعی مدیر یا تراکنش زنده برای آزمون‌های خودکار استفاده نمی‌شوند.

## مسیر ربات

- `/start`: انتخاب اندروید، آیفون، ویندوز یا مک؛ دریافت آموزش و لینک دانلود؛ نمایش هشدار حذف یا جابه‌جا نکردن اکستنشن؛ پرسش خرید با دکمه‌های بله/خیر.
- خرید: نام، نام خانوادگی، تعداد روز، داشتن کد تخفیف و در صورت نیاز کد؛ سپس صورتحساب داخلی بله.
- پرداخت: مبلغ در پایگاه داده محاسبه می‌شود. نمایش پنل به تومان و صورتحساب بله به ریال است. `pre_checkout_query` تأیید پرداخت نیست؛ `successful_payment` به همراه استعلام `inquireTransaction`، تطبیق پرداخت‌کننده، شناسه تراکنش، مبلغ و واحد پول لازم است.
- پس از پرداخت: انتخاب دریافت توکن جدید یا ثبت توکن کاربری موجود. ثبت توکن بدون سفارش پرداخت‌شده امکان فعال‌سازی ندارد.
- تمدید: دریافت توکن کاربری، بررسی تعلق آن به حساب اکستنشن و مشتری، دریافت مدت، تخفیف و پرداخت؛ سپس تمدید از بزرگ‌ترِ زمان فعلی یا تاریخ انقضای موجود.
- `/cancel` یا «منوی اصلی»: خروج از جریان؛ سفارش پرداخت‌شده باقی می‌ماند و از «ثبت توکن پس از پرداخت» قابل پیگیری است.
- پشتیبانی: ایتا و چت آگهی دیوار؛ هر دو لینک در پنل قابل ویرایش هستند.

## پنل

در بخش کد تخفیف، می‌توان «بدون تاریخ انقضا» را انتخاب کرد یا با تقویم شمسی، تاریخ و ساعت پایان اعتبار را به وقت تهران تعیین کرد. تاریخ دقیق به ISO UTC در پایگاه داده ثبت می‌شود و تخفیف‌های نامحدود مقدار `NULL` دارند. فونت همه بخش‌های وب، از جمله فرم‌ها و تقویم، Vazirmatn است.

نمای کلی و روند واقعی درآمد، سفارش‌ها با جست‌وجو و فیلتر و صفحه‌بندی، استعلام پرداخت‌های در حال پردازش، مشتریان، کدهای تخفیف درصدی و ثابت با محدودیت کل و هر کاربر، سه اتصال مستقل، قیمت و وضعیت فروش، لینک‌های چهار سیستم‌عامل، امنیت حساب و گزارش فعالیت.

داده نمایشی یا فروش ساختگی وجود ندارد. داده‌ها از Supabase خوانده می‌شوند. لینک دانلود در حال حاضر برای هر چهار سیستم‌عامل همان لینک ارائه‌شده است؛ در پنل می‌توان برای هر سیستم‌عامل لینک جدا ثبت کرد. آموزش مک به‌صورت پیش‌فرض آموزش کروم ویندوز است و توضیح تفاوت احتمالی محل گزینه‌ها نیز ارسال می‌شود. روش نصب آیفون مطابق آموزش جداگانه است؛ پشتیبانی اکستنشن‌های دسکتاپ در Chrome آیفون فرض نشده است.

## ساختار و استقرار

| مسیر | کاربرد |
| --- | --- |
| `web/` | کد منبع پنل و فونت محلی |
| `index.html` و `assets/` | خروجی تولیدشده برای GitHub Pages در ریشه مخزن |
| `supabase/schema.sql` | ساختار مستقل پایگاه داده؛ فقط برای نصب تازه |
| `supabase/functions/gptyar-bale/` | API مدیریت، احراز هویت، وب‌هوک، اتصال بله و اکستنشن |
| `tests/` | آزمون‌های رمزنگاری، جریان ربات، پرداخت، تمدید و SQL |

```sh
npm ci
npm test
npm run check
npm run build
```

GitHub Pages باید از شاخه `main` و پوشه ریشه (`/`) منتشر شود. فایل `index.html` خروجی است؛ منبع را در `web/` ویرایش کنید و دوباره build بگیرید. همه فونت‌ها و کتابخانه QR همراه خروجی هستند.

سرویس بک‌اند روی پروژه متصل Supabase با نام **`gptyar-bale`** نصب شده است. همه ۱۶ جدول و تمام توابع این سامانه با پیشوند **`gpyb_`** هستند. جدول‌های موجود با پیشوند `gptyar_`، سیستم آموزشی، Supabase Auth و سایر Edge Functionها تغییری نکرده‌اند. مجوز جدول‌ها و RPCها از `anon` و `authenticated` گرفته شده و RLS روی همه جدول‌ها فعال است؛ دسترسی فقط از بک‌اند با `service_role` انجام می‌شود.

برای پروژه Supabase جدید، ابتدا `schema.sql` را فقط یک بار اجرا کنید، URL API در `web/src/app.js` و CSP در `web/index.html` را عوض کنید، مبدأ مجاز را در `index.js` تنظیم کنید و تابع را طبق `supabase/config.toml` منتشر کنید. `verify_jwt=false` فقط به‌دلیل احراز هویت داخلی پنل و وب‌هوک است؛ همه مسیرهای مدیریت به نشست دومرحله‌ای نیاز دارند.

برای تولید لینک راه‌اندازی جدید پیش از فعال‌شدن مدیر:

```sh
node scripts/create-setup-code.mjs
```

SQL چاپ‌شده را در همان پروژه اجرا کنید و لینک چاپ‌شده را فقط در اختیار مدیر قرار دهید. این ابزار نمی‌تواند مدیر فعال را بازنشانی کند.

## امنیت و بازیابی عملیات

رمزها با PBKDF2-SHA256 و ۶۰۰٬۰۰۰ تکرار و نمک تصادفی ذخیره می‌شوند. TOTP استاندارد SHA1، شش رقم و بازه ۳۰ ثانیه است؛ استفاده دوباره از همان کد مسدود است. نشست‌های کامل فقط پس از مرحله دوم صادر می‌شوند، ۸ ساعت اعتبار دارند و توکنشان فقط به‌صورت هش در سرور و در `sessionStorage` مرورگر نگهداری می‌شود. تغییر رمز تمام نشست‌ها را باطل می‌کند.

توکن‌های بله، پرداخت، اکستنشن، کاربر و کلید TOTP با AES-GCM و زمینه جداگانه رمزگذاری می‌شوند. کلید رمزگذاری به‌طور پیش‌فرض با HKDF از کلید سرویس محیط Supabase استخراج می‌شود. برای مدیریت مستقل می‌توان پیش از ورود اولین مدیر، secret با نام `GPTYAR_BALE_ENCRYPTION_KEY` را در تنظیمات Edge Functions ثبت کرد. **تغییر آن یا چرخاندن کلید سرویس بدون رمزگشایی و رمزگذاری مجدد رکوردها، داده‌های قبلی را ناخوانا می‌کند.** هیچ کلید سرویس در مرورگر یا مخزن قرار ندارد.

وب‌هوک از مسیر محرمانه تصادفی استفاده می‌کند. شناسه آپدیت‌ها، تراکنش‌ها، پرداخت‌ها و اشتراک‌ها یکتا هستند. قفل‌های پایگاه داده از پردازش هم‌زمان گفت‌وگو، سفارش و اشتراک جلوگیری می‌کنند. ظرفیت تخفیف در تراکنش رزرو می‌شود؛ سفارش‌های در حال پرداخت تا تعیین تکلیف، رزرو را حفظ می‌کنند.

ساخت کاربر فقط با نام و نام خانوادگی انجام می‌شود. شناسه حساب از پاسخ واقعی اکستنشن پیش از بررسی بعدی ذخیره می‌شود؛ پس از قطع ارتباط، «بررسی و فعال‌سازی» از همین شناسه ادامه می‌دهد و حساب تکراری نمی‌سازد. اگر پاسخ ساخت دریافت نشده باشد، مدیر می‌تواند پس از بررسی نتیجه در اکستنشن، با «تطبیق توکن ساخته‌شده» حساب را مشخص کند. نام، اعتبار، حساب مدیریتی، سابقه تخصیص و فهرست حساب‌های موجود پیش از درخواست بررسی می‌شوند. بدون شناسه یا تطبیق صریح، ساخت دوباره انجام نمی‌شود. در تمدید، تاریخ هدف پیش از درخواست ذخیره می‌شود و تکرار همان تاریخ را اعمال می‌کند.

ارسال توکن جدا از فعال‌سازی ثبت می‌شود. خطای پیام‌رسانی سفارش را از حالت تکمیل‌شده خارج نمی‌کند؛ کاربر با «دریافت مجدد توکن» و مدیر با «ارسال مجدد توکن» می‌توانند آن را بازیابی کنند. صورتحساب نیز پس از خطای ارتباطی قابل دریافت مجدد است و سفارش معتبر به دلیل خطای ذخیره شماره پیام لغو نمی‌شود. شناسه آپدیت، ایجاد سفارش و مصرف تخفیف را در تلاش مجدد یکسان نگه می‌دارد.

## قرارداد اکستنشن

فایل اکستنشن `v4.6.5(2).rar` بررسی شد. اعتبارسنجی توکن مدیریتی نسخه ۴.۶.۵ بر مبنای درخواست `POST /accupdator/validate` با `token` و `version`، هدر `Authorization: Bearer` و سپس تطبیق شناسه حساب با نتیجه `GET /accupdator/subscribers/all` انجام می‌شود:

- `POST https://api.gptyar.com/accupdator/validate`
- `GET .../subscribers/all`
- `POST .../subscribers/create` با `name` و `expiresAt`
- `PATCH .../subscribers/update` با `subscriptionId` و `expiresAt`

شناسه اشتراک برای جست‌وجوی محلی به متن تبدیل می‌شود، ولی نوع اصلی `subscriptionId` از پاسخ اکستنشن جداگانه حفظ و بدون تبدیل در درخواست تمدید ارسال می‌شود. شناسه عددی به‌صورت عدد و شناسه متنی به‌صورت متن ارسال می‌شود. سفارش تمدیدِ نیازمند بررسی با همان تاریخ هدف از «بررسی و فعال‌سازی» در پنل ادامه پیدا می‌کند؛ ثبت سفارش یا پرداخت مجدد لازم نیست.

توکن مدیریتی باید دسترسی معتبر داشته باشد و شناسه حساب در پاسخ اعتبارسنجی و فهرست کاربران یکسان باشد. تغییرات احتمالی نسخه‌های بعدی باید با فایل اکستنشن تطبیق داده شوند. مسیرهای حساس ساخت/تمدید به‌صورت شبیه‌سازی‌شده آزمایش شده‌اند؛ تراکنش واقعی بله و ساخت زنده کاربر به توکن‌های خود مدیر نیاز دارند.


## اصلاح جریان کد تخفیف کامل و نام اکستنشن (۲۳ اکتبر ۲۰۲۶)

- تخفیف ۱۰۰٪ در تابع `gpyb_new_order_v2` سفارش واقعی با مبلغ **صفر تومان** می‌سازد، در همان تراکنش و با رعایت ظرفیت/سهم کاربر آن را به وضعیت `paid` منتقل می‌کند و رویداد `coupon.redeemed` ثبت می‌شود. در این حالت هیچ صورتحساب بله، `pre_checkout_query` یا شناسه تراکنش ساختگی صادر نمی‌شود. سفارش‌های رایگان در مجموع درآمد، صفر لحاظ می‌شوند.
- در تمدید، توکن کاربر به اشتراک متعلق به همان حساب متصل می‌شود و نام نمایشی از اکستنشن خوانده می‌شود؛ ربات دیگر نام و نام خانوادگی را درخواست نمی‌کند. شناسه `[GY:...]` قدیمی فقط هنگام نمایش نام پاک می‌شود.
- ایجاد حساب جدید در اکستنشن فقط با نام و نام خانوادگی ثبت‌شده توسط مشتری انجام می‌شود و شماره سفارش به نام کاربر اضافه نمی‌گردد. چون نام دیگر شناسه یکتا نیست، پس از خطای نامشخص در ایجاد حساب، درخواست مجدد خودکار انجام نمی‌شود؛ سفارش به بررسی انسانی نیاز دارد تا کاربر تکراری ساخته نشود.
- برای ارتقای پایگاه داده، migration `supabase/migrations/20261023_free_coupons_and_extension_names.sql` را در پروژه مربوطه اعمال کنید؛ `schema.sql` تمام ارتقاها را برای نصب اولیه در بر دارد و نباید دوباره روی پایگاه داده موجود اجرا شود.
- بررسی‌های خودکار: `npm test`؛ آزمون‌های توکن مدیریتی/کاربری، کد تخفیف کامل، نام تمدید و وضعیت مبهم ساخت حساب.

## اصلاحات پایداری و بررسی‌ها

ارتقای `20261023_reliable_checkout_and_recovery.sql` ستون‌های بازیابی و تحویل و توابع محدودشده به سرویس را اضافه می‌کند؛ اطلاعات قبلی پاک نمی‌شوند. مسیر RPCهای دارای عدد و پاسخ واقعی PostgREST اصلاح شده است. ثبت توکن و مشخصات اتصال، تغییر رمز و ابطال نشست‌ها، و فعال‌سازی مدیر و ذخیره کدهای بازیابی به‌صورت تراکنشی انجام می‌شوند. آمار تخفیف مستقیماً در SQL محاسبه و صفحه‌بندی می‌شود؛ محدودیت ۱۰۰۰ ردیفی REST روی شمارش آن اثر ندارد. توکن جدید همان اشتراک، شناسه و مالک قبلی را حفظ می‌کند.

تقویم شمسی یک منبع در `web/src/coupon-calendar.js` دارد و همراه build بسته‌بندی می‌شود. سال بدون جداکننده، طول ماه‌های ۲۹/۳۰/۳۱ روزه، مرز نیمه‌شب تهران و تبدیل دقیق ساعت به UTC بررسی می‌شوند. همه متن‌ها و کنترل‌ها از Vazirmatn محلی با وزن درست استفاده می‌کنند.

`npm test` شامل آزمون‌های منطق ربات و خطاهای شبکه، قرارداد استخراج‌شده از اکستنشن، رمزنگاری و پرداخت، فرم‌های واقعی در DOM، و Postgres مستقل در حافظه با PGlite است. آزمون‌های پایگاه داده روی اطلاعات مشتریان اجرا نمی‌شوند. `npm run check` نحو همه ماژول‌ها را بررسی می‌کند و `npm run build` خروجی Pages و وجود فایل‌های ارجاع‌شده را تأیید می‌کند.

آزمون DOM جای بازبینی بصری مرورگر را نمی‌گیرد. سرویس پیش‌نمایش محیط در دسترس نبود؛ تراکنش بانکی و ساخت حساب واقعی برای آزمایش اجرا نشده‌اند. اعتبار توکن پرداخت همچنان با تراکنش واقعی مشخص می‌شود.
